# خارطة طريق تطبيق الموبايل — Shubayr

آخر مراجعة: **2026-09-30** · العقد المدمج من الفريق: **API 8.2.0**.
توافق Flutter الكامل مع 8.2 **غير مكتمل**؛ آخر تكامل وظيفي مستهدف كان 7.1.

هذه خارطة عمل Flutter الحالية، وتحل محل خطط الإدارة المتقدمة داخل الهاتف.
علامة `[x]` تعني أن التنفيذ موجود في الكود، ولا تعني وحدها اكتمال الاختبار
على الخادم الحقيقي أو الجاهزية للنشر. بنود القبول والتشغيل أدناه مستقلة.
حالة قاعدة البيانات ونتائج الفحوص هي آخر حالة موثقة بتاريخ المراجعة، وليست
فحصًا حيًا يتجدد تلقائيًا.

## 1. نطاق التطبيق المعتمد

| المستخدم | العمل المسموح في الهاتف |
| --- | --- |
| الزائر | تصفح المتجر والمنتجات وتسجيل الدخول |
| الزبون | التسوق والطلبات والعناوين والمفضلة والتقييمات والمرتجعات والحساب |
| مندوب التوصيل | متابعة توصيلاته وتنفيذ إجراءات التوصيل التي يسمح بها الخادم |
| مراقب الطلبات | الاطلاع على الطلبات وتفاصيلها والإشعارات، دون تعديل إداري |

إدارة المنتجات والمستخدمين والمخزون والمشتريات والمالية والتقارير وإعدادات
المتجر تنفّذ في Web Admin المنفصل. لا تُعاد إضافتها إلى Flutter.
إعدادات الحساب الشخصية تبقى ضمن تطبيق الهاتف.
Chrome معاينة تطوير مستقلة لتطبيق الهاتف؛ واجهتا متجر الويب وWeb Admin
مشروعان منفصلان عن Flutter.

- [x] خيار `iOS + Web Admin (Remote)` لتشغيل الإدارة والمحاكي معًا وإيقاف جلستي التصحيح معًا،

- [x] قبول أدوار `customer` و`delivery_agent` و`order_monitor` على سطح `app` فقط.
- [x] منع حسابات العمل من دخول مسارات التسوق، وتوجيه كل دور إلى واجهته.
- [x] تجديد الجلسة وتنسيق الطلبات المتزامنة، ومسح بيانات الدخول ومحاولة إلغاء
  جلسة الخادم عند الخروج؛ إلغاء جلسة الخادم يحتاج اتصالًا.

### واجهات الزبون الحالية

البنود التالية منفذة وفق التكامل السابق؛ نجاح اختبارات Flutter لا يثبت توافقها
مع كميات وأسعار SKU الجديدة في 8.2. مهام الترحيل أولوية في القسم 4.

- [x] التصفح والأقسام والبحث والمنتجات والفلاتر والعروض وفق العقد المتاح.
- [x] السلة والعناوين وإتمام طلب الدفع عند الاستلام.
- [x] قائمة الطلبات والتفاصيل والتتبع والإلغاء وفق القواعد الحالية للخادم.
- [x] المفضلة والتقييمات ومسارات المرتجعات الحالية والملف الشخصي.
- [x] إزالة واجهة التفاوض؛ أزال الفريق التفاوض من عقد 8.0، وما زالت إزالة حقوله القديمة من نماذج Flutter مطلوبة.
- [x] إظهار حالة الطلب «مرفوض» ودعمها في الفلاتر دون إضافة إجراء رفض إداري.
- [x] اعتماد عملة المورد في عرض المنتجات والسلة وطلبات الزبون وإتمام الطلب
  وأجور التوصيل، مع الرجوع إلى إعدادات المتجر عند غياب الحقل في البيانات القديمة.

هذه البنود تمثل الرحلات الموجودة حاليًا، ولا تغطي تلقائيًا قواعد دورة الطلب
والمرتجعات الجديدة المؤجلة إلى مراحل الخادم التالية.

### المتابعة والتوصيل والإشعارات

- [x] مراقب الطلبات: قائمة للقراءة فقط مع البحث والحالة والتاريخ والعدادات والصفحات.
- [x] تفاصيل المراقبة: بيانات الزبون والعنوان والمواد المحفوظة والمبالغ، دون صور
  المنتجات أو أزرار التنفيذ الإداري.
- [x] مندوب التوصيل: قائمة توصيلاته مع تحميل المزيد وتحديثات الحالة الموجودة حاليًا.
- [x] فلترة توصيلات المندوب حسب الحالة عبر الخادم، وإعادة الصفحات عند تغيير الفلتر،
  وتصفير الفلتر عند تبديل الحساب، وتجاهل نتائج الطلبات القديمة.
- [x] إجراءات التوصيل المطابقة للعقد: مسند → قيد التوصيل، ثم تم التسليم أو فشل،
  وتم التسليم → مرتجع. لا تظهر إجراءات للحالات النهائية أو غير المعروفة.
- [x] إعادة جلب القائمة عند تعارض `409`، وإعادة تحميل نتائج الفلتر بعد تحديث الحالة
  حتى يعكس العدد والصفحات بيانات الخادم. الخادم وحده يتحقق من جاهزية الطلب للإرسال.
- [x] صندوق إشعارات محفوظ بالعربية والإنجليزية، وعدّاد غير المقروء، وقراءة الإشعار
  منفردًا وروابط تناسب دور الحساب.
- [x] مزامنة الإشعارات كل 30 ثانية أثناء نشاط التطبيق وعند العودة إليه.

المزامنة أثناء نشاط التطبيق لا تعني اكتمال Push عند إغلاق الهاتف للتطبيق.

## 4. متبقٍ في Flutter ويمكن تنفيذه بالعقد الحالي

الترتيب المقترح بعد دمج تحديثات الفريق:

| الأولوية | العمل | العقد المتاح / معيار الإكمال |
| --- | --- | --- |
| 1 | توافق الكميات وSKU في API 8.2 | حفظ الكسور حتى 3 منازل دون `toInt()` في السلة والطلبات والمراقبة والمرتجعات والتوفر، واحترام `whole_units_only` و`base_unit` وربط الاختيار بمعرّف SKU. |
| 2 | أسعار وتوفر SKU والعلامات التجارية | قراءة `effective_price` و`availability` لكل SKU، وربط العلامات والفلاتر بالعقد الجديد وإزالة حقول التفاوض القديمة؛ لا يحسب الهاتف التسعير مستقلًا. |
| 3 | شاشة تفضيلات الإشعارات | قراءة وتحديث `/me/notification-preferences`، وحفظها للحساب؛ لا يوصف حفظ التفضيل بأنه تفعيل لخدمة Push غير المجهزة. |
| 4 | عملة تفاصيل المراقبة | أصبح حقل `MonitorOrderDetail.currency` موثقًا في 8.2؛ ربطه في Flutter ما زال مطلوبًا. |
| 5 | رصيد الولاء وسجل النقاط للزبون | `GET /loyalty` مع الصفحات والحالات الفارغة والأخطاء. لا نعرض النقاط كخصم فعلي على الطلب؛ العقد الحالي لا يجعل الاستبدال تخفيضًا للفاتورة. |

لكل بند: تنفيذ وربط Remote، اختبارات سلوك مناسبة، تحليل، ثم تحقق حي وقبول
الواجهة قبل تسجيله كمكتمل. لا نضيف بيانات عميل/عنوان لشاشة المندوب اعتمادًا
على افتراضات؛ عقد `Delivery` الحالي محدود، والتفاصيل الأغنى تحتاج توسعته.

## 6. قبول تحديث واجهة المندوب — 2026-09-29

التنفيذ والاختبارات في ملفات `features/delivery`؛ لم يتغير كود الخادم أو لوحة
الإدارة أو عقد API، ولم تُضف اعتماديات. استُخدم نمط Repository وRiverpod القائم،
مع `ChoiceChip` مثل فلاتر الطلبات، ومكونات القوائم والحالات وsnackbar المشتركة.

- [ ] اختيار طريقة الفحص البصري مع أحمد: يدويًا أو بواسطة Codex على المحاكي.
- [ ] عبر حساب مندوب فعلي، تجربة «الكل» وكل حالة، والفراغ والخطأ وإعادة المحاولة
  والصفحات، والتأكد أن تغيير الفلتر يعيد موضع القائمة ولا يخلط النتائج.
- [ ] تجربة مسند → قيد التوصيل لطلب جاهز، ورفض الإجراء لطلب غير جاهز، ثم التأكد
  أن التطبيق يعرض سببًا مفهومًا ويعيد قراءة القائمة دون ادعاء نجاح التحديث.
- [ ] تجربة قيد التوصيل → تم التسليم أو فشل، وتم التسليم → مرتجع على بيانات اختبار
  مناسبة؛ هذه إجراءات حقيقية تؤثر في الطلب، فلا تُجرّب على طلبات إنتاجية.
- [ ] ضمن فلتر، التأكد من اختفاء التوصيل الذي تغيّرت حالته وظهور تأكيد الحفظ،
  مع بقاء إمكانية إعادة المحاولة إذا تعذر تحميل القائمة بعد حفظ ناجح.
- [ ] فحص العربية/الإنجليزية والوضعين والنص الكبير وتغيير العرض، ثم تبديل الحساب
  للتأكد من تصفير الفلتر وعدم عرض بيانات المندوب السابق.

لم يُجرَ القبول الحي أو الفحص البصري لهذا التحديث بعد؛ لا يُعامل اكتمال الكود
والاختبارات الآلية على أنه اكتمال هذين البندين.
